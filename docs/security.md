# Security Architecture

## Key model

| Key | Used for | Can bypass RLS? |
|---|---|---|
| `SUPABASE_SERVICE_ROLE_KEY` | All server-side DB + Storage operations (Drizzle client, storage helpers) | Yes — by Supabase design |
| `NEXT_PUBLIC_SUPABASE_ANON_KEY` | Supabase Auth only (login/signup on the client) | No |

The anon key **never** queries business data. It is only used by `@supabase/ssr` for session management.

## Row-Level Security

RLS is enabled on all 13 public tables with **no permissive policies**. This means:
- `anon` and `authenticated` roles: all SELECT/INSERT/UPDATE/DELETE blocked (verified: returns `42501`)
- `service_role`: bypasses RLS (all server operations work normally)

Migration: `drizzle/custom/0002_rls_security.sql`

If realtime subscriptions or client-direct queries are ever needed, add scoped policies tied to `auth.uid()` → `account_id` **before** enabling that access path.

## audit_log immutability

A DB trigger blocks UPDATE and DELETE on `audit_log`. Migration: `drizzle/custom/0001_audit_log_immutability.sql`.

## Storage

Bucket: `coi-files` (private, 10 MB limit, PDF/JPEG/PNG/TIFF only).

All client access goes through short-lived signed URLs generated by the service-role client. The bucket has no public access. See `lib/storage/client.ts`.

## Multi-tenant isolation

Every tenant-scoped query in the application is filtered by `account_id` sourced from the authenticated session — never from the request body. The `account_id` is resolved server-side from `auth.uid()` → `users.account_id`.

Cross-tenant isolation test: `tests/security/cross-tenant-isolation.test.mjs` (runs in CI).

## Webhook security

Stripe webhooks: `lib/payments/webhooks.ts` requires `verifyAndParseWebhook()` to succeed before any event processing. Unverified bodies throw → the route handler returns 400.

Inbound email webhooks: provider signature verification is required (implementation TBD when email provider is chosen).

## What is NOT in scope (v1 legal boundary)

This product **collects, extracts, matches, alerts, and tracks**. It does **not** advise on whether coverage is adequate. See `docs/rejected.md` for the boundary log.
